# 全新 Bandori 组曲基础设施

English version: [bandori-medley-foundation.md](bandori-medley-foundation.md)

## 依据与范围

本文规定 `dev/medley-v2-greenfield` 新计算器共用的输入与计分规则。代码完全新写，不导入、包装或重构旧组队器计分与搜索。HHWX 已有输入和产品规则仍须遵守，旧求解器及实验分支的架构不具有权威性；来源检查会约束 TypeScript 的导入边界。

计分采用 Bestdori 的平均判定／技能倍率方法，加上下文明确约定的 HHWX 组曲规则。它既不是原生游戏模拟，也不是照搬 Bestdori 单曲计算器。游戏实际表现只作记录，未经重新讨论不得写进实现。

每个完成且可审查的模块都应及时提交，便于追溯和回退。文档中的失效说明直接重写，改动历史交给 Git，不堆叠补丁段落。审计者先读本文和当前新实现；主 agent 必须独立复核其结论。

## 输入与职责

调用方提供 HHWX 现有档案、原始主数据、三首有序歌曲及谱面、活动设置和 PERFECT 百分比文本，不负责预计算卡牌参数、加成或队伍总值。

- HHWX 档案中名为 `bestdoriProfile` 的字段，用 compression v2 保存卡牌持有／等级、突破、技能等级、剧情、训练／卡面／排除状态和区域道具等级。这只是我们自己档案中的一个字段，不是另一种 Bestdori 导入／导出输入。
- 潜能与角色任务加成只读 HHWX 档案顶层的 `characterPotentials` 和 `characterMissionBonuses`。
- 参数来自原始卡牌、角色、技能、道具、歌曲及活动记录。Cards 区服扩展按档案区服解析，区服缺失时保留既有的 JP 回退规则。
- 歌曲 ID 严格转成正数 u32；PERFECT 文本先转成规范的十进制概率。

`hhwx-medley-search-source-v1` 准备完整持有卡池及合法的已拥有道具配置。三支队伍、队长和最终共用道具配置都是搜索输出，不是前端必填项；此检查点尚未实际接通前端／API。

`hhwx-medley-foundation-source-v1` 是极小固定队验算入口，额外指定 15 张拥有的卡、三支队伍和一套道具。它生成的 Rust 输入 `hhwx-medley-scoring-input-v1` 只含连续实例 ID、已解析技能、队伍综合力和谱面；它是参考计分工具，不是搜索请求。

档案压缩损坏、选中主数据缺失、引用错误、不支持的自有字段或版本，返回错误码和字段位置；原始主数据中的未使用字段可以存在。输入错误不是“无解”。排除标记不改变显式固定队的分数，但搜索会在生成候选前硬排除这些卡。

## 已确定的产品规则

- 三个有序歌曲槽，允许重复，不允许换序。
- 每队五个不同角色，同一物理卡不能跨队复用；输出的成员索引 2 是队长。
- 三队共用算法选出的同一套已拥有道具：一个乐团组、一个属性组及一个可选参数道具。国服元数据中的 59、68、72 不进入计算器。
- 正式目标只有平均分总和的、已证明的 Top-1；同分选一个稳定代表。理论最高分不是第二目标。
- 可以被动保留最多十个已发现方案，包括最优结果，但不是证明过的全局 Top-10。后续理论最高分只对这小组方案补算；此输出补全过程尚未实现。
- 只有全部空间已穷尽或安全剪枝才算正式成功。取消、超时、内存、数据或运行时失败均为未完成；`bestSoFar` 仅供诊断，没有按差距判成功的模式。
- 保留既定的成员、道具和浮点运算顺序。

约 2,000 卡是未来困难验收，不是早期或默认测试规模。该场景目标仍为 300 秒、具有竞争力的 200–300 MiB 增量内存，以及低于 1 GiB 的硬峰值。先用极小输入确认正确性，超时不算成功。

暂定搜索方向是提前约束三支部分队伍的整套分数上界、限量尝试完整方案提高当前分数，以及短期保存完整小块候选和固定容量计分缓存。这些工程做法可以复核推翻，不是游戏规则。Calc 只用于借鉴剪枝位置和数据存活时间，不定义 HHWX 计分与最优证明；细节见[搜索设计](bandori-medley-search.zh-CN.md)。

## 参数、技能与谱面

输入处理按以下顺序推导参数：

1. 从 Cards 最低／最高 P/T/V 行，按 Bestdori 稀有度成长曲线和 JavaScript `Math.round` 还原所选等级。
2. 每项加入 `50 * rarity * masterRank`，再加入训练与已完成剧情加成。
3. 把压缩任务单位从十分之一百分点换算回来。潜能贡献单独 floor；收集与训练任务倍率先相加，再对任务贡献 floor 一次。三项 P/T/V 恰好相同也不切换规则。
4. 按持有等级、区服 P/T/V 倍率及目标乐团／属性计算道具。
5. 计算活动属性、角色、规范成员 `situationId`、突破、匹配参数和房间加成。
6. 按 JavaScript 数值运算相加卡牌、道具、活动贡献，得到 `deckTotalParameter`；这里不额外对道具／活动贡献取整。

技能数值优先读档案区服，只有槽位缺失才回退 JP，显式零保留为零。道具倍率只读当前区服，向下寻找不高于持有等级的最近可用行。

技能取第一个识别出的计分行，包括零值；完整五人确定后解析同团／同属性条件；持续技能另保留后续普通计分行作为降档倍率。计分类型为 `neutral`、`score`、`score_on_perfect`、`perfect_only`、`continued_perfect` 和 `great_or_worse_half`。普通计分技能可带布尔值 `isRateUpWithPerfect`；固定增长量和上限写在计分公式中，不再让调用方提供。

没有生命输入，也没有生命状态。原始 `score_over_life` 和 `score_under_life` 按来源顺序作为普通计分行，不检查生命阈值，也不假定生命值。

谱面保留 Single／Directional、Long 两端、Slide 两端及没有 `hidden` 属性的中间节点。BPM 用来把拍数转成秒，其余类型包括 System 不计分。`skill` 属性只要存在就表示触发，即使值为 false。同拍先放触发音符；每曲恰好六次触发，秒数有限且非负，等级读取歌曲主数据，等级 5 也有效。

## 计分公式

规则标识为 `hhwx-medley-bestdori-v2`。`p` 是 PERFECT 概率，`n` 是当前技能窗口内覆盖的音符数，包含正在计分的音符，从 1 开始：

```text
judge = 1.1 * p + 0.8 * (1 - p)
基础系数 = (3 + 0.03 * (谱面等级 - 5)) / 音符数
base = 队伍综合力 * 基础系数
基础音符分 = floor((base * combo倍率) * judge)
窗口增分 = floor(基础音符分 * 技能倍率) - 基础音符分
歌曲分数 = 基础音符分之和 + 各窗口增分之和
```

概率先进入倍率，再进行两次取整。没有 P/G 分支树、历史状态分布或“每个判定分支取整后求期望”。

基础加分百分比为 `C` 时，普通倍率是 `1 + C / 100`。逐音符增长先把 `C` 改为 `C + 0.5 * min(n, 100) * p`。持续技能使用 `降档倍率 + p^n * (正常倍率 - 降档倍率)`。区分 PERFECT／GREAT 的技能使用：

```text
(1.1 * PERFECT时倍率 * p + 0.8 * GREAT时倍率 * (1 - p)) / judge
```

两个倍率相同时直接用该倍率。三种条件技能的 PERFECT 倍率都是 `1 + C / 100`；GREAT 倍率在 `score_on_perfect` 中为 1、`perfect_only` 中为 0、`great_or_worse_half` 中为 0.5。

Combo 跨三曲延续：

```text
combo <= 20    : 1.00
combo <= 50    : 1.01
combo <= 100   : 1.02
combo <= 300   : 1.01 + floor((combo - 1) / 50)  * 0.01
combo <= 3000  : 1.04 + floor((combo - 1) / 100) * 0.01
其他           : 1.34
```

前五次触发的 120 种顺序等概率，第六次重复队长技能。窗口从现有排序中触发音符的下一个音符开始，因此后面的同时间音符也生效；终点为 `音符时间 <= 触发时间 + 时长`，不加 epsilon。重叠窗口分别计数、分别取整增分后相加，不替换、不合并倍率后取整，也不另加截零操作。

设 `B` 为歌曲基础整数总分，`E[窗口][成员]` 为各窗口整数增分。歌曲平均分按 `(5 * (B + E[5][队长]) + 前五窗所有成员的E之和) / 5` 计算：分子先用有符号 i128 精确累加，只转换一次浮点数，再除以五。这是 120 种顺序期望约去公因子 24，并没有近似随机顺序的概率。最终均值不取整，三曲仍按 `(歌曲0 + 歌曲1) + 歌曲2` 相加。

倍率计算使用 binary64，不改写既定运算顺序。基础音符分及单个技能作用后的音符分必须在 u32 范围内，窗口增分可以为负；有符号 i128 足以容纳 u32 音符数下的全部总和与均值分子。非法或溢出的标量运算就失败，不回绕。不包含 GOOD／BAD／MISS、断 combo 或生命行为。

## 来源证据与明确边界

已固定的 [Bestdori 主包](https://bestdori.com/js/app.d390adb1.js) 模块 `c0f0`，SHA-256 为 `ac84605d7889e53c0144ab7c41e379c174b94b8dc31edae07f3483b8a0610778`，于 2026-08-31 复核。其 `st → lt → ct` 由 [ToolTeamBuilder](https://bestdori.com/js/ToolTeamBuilder.6367a448.js) 正式结果路径调用，不只是预览；它是平均倍率、两次取整、持续技能和逐音符增长公式的依据。

上游这条路径仍是单曲计算器，使用普通 combo、不同队长位置和单个生效窗口。HHWX 保留本文规定的组曲 combo、索引 2 队长和独立窗口取整后相加，也保留“首个识别行／显式零”处理，不采用上游依赖数值是否为零的部分回退规则。另经明确决定，保留 `score_only_perfect`（`perfect_only`，GREAT 倍率为 0），以支持未来可能使用该既有主数据定义的卡牌，尽管上游 `st` 不识别它。独立窗口取整是明确批准的复杂度取舍：放弃重叠处微小的联合取整差异，降低搜索中反复计分的开支。这些是明确保留的兼容边界，不能把“对齐”说成整套实现完全相同。规则版本用来区分旧的标准化输入和结果；输入字段形状不变。

先前原生审计使用 JP 10.1.3、主数据 `20260805110509`、技能效果 SHA-256 `d98e76c0198a6a714be1d38e4696a044242c8384b905426a311c8c2b0961aebc`。以下发现仍不实现：有偏的 1,024 路径／96 种可达排列、单精度计分与 combo 主数据表、生命条件触发、逐帧技能时间及冲突处理。它们是来源记录，不是待办任务。

## 验证检查点

保留的 15 卡、每曲七音符用例验证 HHWX 原始输入经 TypeScript 转换后进入 Rust。现有小用例检查参数与加成取整、谱面、技能公式、窗口边界和直接叠加。另有六条直接来自固定上游函数的极小数值对照，覆盖平均判定、条件技能、持续、增长封顶及两次取整。

参考实现刻意逐顺序、逐音符计算，输出一份基础整数音符分、各顺序分数、combo 起点及浮点位值，不再输出判定状态。生产计分按 combo 分段合并恒定倍率、复用独立窗口增分，并用极小输入与参考对照。公式纠错只做这些针对性检查及极小穷举，不自动重跑长时间真实档案基准。前端／API 接入和后续搜索改动各自另定范围。

# 单曲组队计算器

English version: [single-song-algorithm.md](single-song-algorithm.md)

单曲搜索现在运行于组曲 Rust/WASM 包，复用[组曲规则与计分](medley-foundation.zh-CN.md)中的档案／主数据规范化、卡牌参数、区域道具配置、条件技能解析和精确技能区间计分。旧 TypeScript 单曲搜索及其独立谱面、计分、上界模块已退役。卡牌详情和档案编辑仍使用通用卡牌计算器。

## 目标与结果

分数目标是**合法站位中的最高期望分数**，使用下文依赖位置的顺序分布。`eventPoint` 将此期望代入既有活动公式，按活动类型计入加成与任务支援；不是逐顺序结算 Pt 后求期望。对邦／团队演出仍使用分数关联目标；名次、胜负和 Live Boost 改变展示的 Pt 选项。

主队恰好五张不同角色的实体卡，不使用已排除卡，整队共用一个已拥有的道具配置。最低队长倍率和综合力约束保留；队长资格以完整队伍的实际条件判断，不使用不能触发的条件最大倍率。自身卡牌队长位于第三位，即索引二；这不限定协力房间站位。

规范化前，Worker 对持有卡仅应用计算器明确设置的排除，忽略已保存档案中的排除标记。临时卡覆盖同 ID 持有卡且不被排除。已保存档案及其排除标记不变；共享来源适配器遵守 Worker 传入的有效排除标记。

个人演出结果卡片顺序直接表示最优卡牌站位，协力另外输出最佳玩家站位。`averageScore` 存放该站位未取整的加权期望，页面标为**期望分**。分数目标直接比较它，Pt 目标先比较 Pt 基数、再比较期望，房间分也采用同一玩家站位。后续平局依次比较综合力、卡牌实体 ID 字典序、按房间位置排列的玩家身份、道具配置索引。展示倍率变化不要求重算搜索。

保留队伍还输出当前站位最低分、同五卡同配置所有合法站位中的可达最高分、实现该分数的站位和发动顺序，以及该站位的最高分概率与期望。最高分方案可以在约束内改变队长，依次最大化最高分、最高分概率、期望，再按稳定实体 ID 决胜。概率汇总所有并列最高分顺序，包括等效技能的不同排列。

个人演出的站位与发动序列引用主结果卡片上的编号。这是搜索后的分析，**不会在整个卡库搜索最高分最大的队伍**；独立最高分搜索是后续增强。`resultLimit` 保持 1–50。`exact` 证明给定数据／模型内的最优解或无解；其他结果是发现的备选，不是经过证明的全局前 N 名。`incomplete` 保留具体原因和已找到的结果，补算重新核对保留队伍，不一致即报错。

补算同时保留 `currentMaximumProbabilityNumerator`，表示搜索结果当前站位达到同一个全队可达最高分的概率，沿用现有分母。当前站位不能达到该分数时为零，不改用该站位自身较低峰值的概率。个人演出中，常规站位与最大概率站位不同时，页面分两行展示；相同时只显示一项。协力演出隐藏“最高分方案”和“最高分概率”，保留最佳玩家站位和分数区间；Worker 在两种模式下仍返回峰值字段。不增加搜索轮次，也不改变计分规则。

## 技能顺序与站位优化

已审计的个人演出初始化等价于：

```text
order = [0, 1, 2, 3, 4]
for i = 0 .. 4:
    member = order[i]
    删除 member
    将 member 插入独立均匀整数 [0, 4) 指定的位置
```

共 1,024 条随机路径、96 种结果顺序。每轮读取已经修改过的列表，不是原始成员 i；删除后才抽取位置，整数上界不包含。个人演出的第六次发动属于队长。

前五次发动的边际权重如下，每项除以 1,024，每行、每列之和均为 1,024。

| 发动／原始位置 | 1 | 2 | 3 | 4 | 5 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 192 | 291 | 144 | 141 | 256 |
| 2 | 192 | 243 | 176 | 157 | 256 |
| 3 | 192 | 198 | 200 | 178 | 256 |
| 4 | 192 | 156 | 216 | 204 | 256 |
| 5 | 256 | 136 | 288 | 344 | 0 |

发动时间不依赖顺序时，令 C[w,c] 为已取整的卡牌／区间贡献，站位目标是五个位置／卡牌权重之和，中央卡另加 `1024*C[5,c]`，再加固定基础分。32 状态分配 DP 通过 80 次转移求出最佳站位。排队时间采用下文额外的精确路径；前面的发动者会改变后续窗口时，仅用边际权重矩阵不足以计算期望。

该分布独立复现于留存 arm64 二进制，标签为 JP 10.1.3 和 CN 9.4.3，SHA-256 分别为 `66c9c666c50962b662df8d894e851c7d18f07142dca145cfac3d30d063d1d9fa`、`1d798715a62f804cfa6696b02a8fc3e060abbb2e04877a50c26fc7ad6c7f2a02`。`InGameSkillNoteController.SetupSkillCharaList` 的 RVA 分别为 `0x3307b58`、`0x335969c`。版本标签来自留存审计元数据，直接核验对象是二进制；这不构成当前所有客户端版本及区服的一致性证明。

协力使用自己的队长和四位外部玩家技能，以房间站位顺序初始化相同的 1,024 路径／96 顺序分布，优化全部 120 种玩家站位。玩家编号 1 表示自己，不代表固定占据房间第一位；外部输入对应玩家 2～5。调整自己的副卡不会改变玩家站位。每名合格自身队长与玩家排列均按所选分数／Pt 目标评估，自身与外部玩家期望使用同一站位。第六技能始终跟随所选玩家身份，换位不会改变发动者。外部玩家独立提供“条件满足”开关，不继承自己队伍的条件；未选使用基础技能。`orderModel: "weighted_room"` 替换旧均匀假设，概率分母为 1,024；继续复用相同时间表和单队搜索，没有新增独立协力搜索器。

协力玩家站位和发动序列引用玩家编号，与自身卡牌站位分开。结果保留最佳及最高分玩家站位，最低分采用当前所选站位，最高分概率采用最高分站位；最高分平局最后再按稳定玩家身份决胜。WASM 的 `playerFormation`、`peakPlayerFormation` 使用从零开始的玩家身份（个人演出为 null），Worker 转为 1～5 展示；持久化 `self`／`other1`～`other4` 的身份含义不变，仅调整标签。

## 技能排队时间

单曲现在计入**前一个技能结束后**的 0.75 秒等待，覆盖个人演出、协力和第六次技能。对六个实际发动者：

```text
start[0] = triggerTime[0]
end[w] = start[w] + duration[actor[w]]
start[w+1] = max(triggerTime[w+1], end[w] + 0.75)
```

技能排队不会丢弃发动，延迟会递归传递；持续时间和解析计分中的覆盖音符计数均从实际开始处起算。排到谱面结束之后的技能没有得分贡献。所有技能都占用解析所得的持续时间，包括不加分技能。不提供时间机制开关，第六技能也不豁免。

上述留存 JP／CN 二进制将结束状态倒计时写为 float 位模式 `0x3f400000`（0.75），回到空闲后才启动队首技能。相关 JP 的 playing／finishing／queue RVA 为 `0x33228c4`、`0x3322924`、`0x3322bc4`／`0x33236b0`；CN 为 `0x3378af8`、`0x3378bb0`、`0x3379650`。本实现采用上述连续时间递推，不逐帧模拟 `deltaTime`。这是明确的正常演出计分模型；机器码证据确认等待和队列机制，不证明帧边界处音符处理的精确顺序。

用四条路径控制成本，均不近似期望：

| 时间情形 | 精确计算方法 |
| --- | --- |
| 最长技能仍有足够间隔 | 原固定窗口分配算法。 |
| 所有发动者持续时间相同 | 一次性移动六个窗口，继续使用原分配算法。 |
| 只有第六次可能移动 | 每个合格队长的分配矩阵增加 `weight[4,position] * encoreExtra[leader,lastActor]`，至多做五次分配。 |
| 前五次窗口已依赖顺序 | 按发动者、窗口序号、实际开始时间缓存贡献；每名队长至多计算 120 个顺序，共五名队长，再用 96 种顺序权重计算各站位。 |

期望和保留结果的最高分／概率共用这些表。综合力相同的队长共用计算，binary64 综合力不同则分别计算。一般情形比固定窗口更贵；此次改动不代表分数／Pt 搜索性能优化已经完成。

## 计分范围

角色参数对齐组曲 v4：潜能加成与收集／培养任务合计加成分别向下取整。单曲规则升级为 `hhwx-single-medley-foundation-v4`，在 v3 上加入协力加权站位优化。规范输入使用当前适配器重新生成，旧 v3 均匀房间结果不能作为协力新结果的等值基线；存档格式不变。

综合力保留小数参与计分、约束和排序；只在总合力显示及卡片数字上使用共用的 float32 转换后截断函数。任务支援显示 `floor(rawSupportPower)`，Pt 仍使用原值。分数期望在内部不取整，通用整数格式化函数不变。这是显示对齐，不是原生 float32 计分模拟。

已退役的 Bestdori 兼容单曲调用方曾在计分前对综合力向下取整；迁移后的计算器明确采用组曲的小数综合力契约。支援计分则保留既有的 Bestdori 兼容规则：[已审计的国服原生支援路径](medley-foundation.zh-CN.md#国服原生综合力显示与计分边界2026-09-14)会先截断每张卡的演出／技巧／形象支援贡献，再求和；HHWX 在搜索和 Pt 计算中保留这些贡献的小数。仅对显示合计值向下取整，不等于模拟原生逐参数运算。

在该 CN 9.4.4 二进制中，`EventSupportBandUtility.calculateEventSupportBandDetail`（`0x341c77c`）将每张卡的演出／技巧／形象分别乘以 float32 支援倍率，在 `0x341ca84`／`0x341ca88`、`0x341caac`／`0x341cab0`、`0x341cad4`／`0x341cad8` 分别截断。`EventSupportBandData.CalculatedTotalParam`（`0x35de1c0`）合计这些整数，`CalculateEventSupportBandTotalParam`（`0x341d7a0`）再合计各卡整数，供 `EventSupportBandDialog.initializeTotalParam`（`0x35b89e8`）显示。

每个队长的参数累加顺序与组曲一致：实体 ID 升序后将队长移到索引二。卡牌、道具、活动贡献使用同一函数和运算次序；重排其余站位改变的是发动分布，不改变这项参数累加约定。不同队长的综合力即使只差一个浮点舍入位，也保留到约束、排序和最高分补算。

谱面遵循组曲规范化：Single／Directional、Long／Slide 计分端点、按属性是否存在判断技能触发、同拍触发优先稳定排序、BPM 变化点锚定时间。必须恰有六个触发音符；System 是元数据，不是计分音符。

触发音符不享受自己发动的技能。未延迟发动时，排序在后的**同时刻计分音符确定受益**；排队发动时，实际开始时刻的音符也包含在内：覆盖条件为 `noteIndex > triggerIndex` 且 `start <= note.time <= start + duration`。原触发与延迟开始之间的音符不享受这次技能。不使用旧的 10 微秒容差。单曲 Combo 从零开始，上限 1.11；适用的 Fever 在包含起止端点的区间内令音符分数翻倍。

共享计分器保留 binary64 算术和分阶段向下取整：

```text
coefficient = (3 + 0.03*(playLevel - 5)) / 计分音符数
inner = floor(((teamPower * coefficient * combo) * 平均判定倍率) * fever)
extra = floor(inner * 技能倍率) - inner
顺序分数 = sum(inner) + sum(所选区间贡献)
```

PERFECT／GREAT 效果、持续 PERFECT 与增长技能沿用组曲解析化简。不采样判定序列，不分别结算 P/G 后求期望，不跟踪生命／技能状态，不模拟断连或原生 f32。概率只描述模型下的技能顺序，不表示真人恰好打出原生分数的概率。共享内核仍把各窗口独立取整的贡献相加；单曲排队后不会再同时发动重叠技能，组曲保留原有重叠贡献相加策略。

协力房间分将外部综合力对应的不取整得分估计加入自身原始期望，再统一向下取整，保留仅用于房间分的 `1e-5` 容差。任务支援从剩余卡中选至多五个不同角色，排除主队实体卡和已排除卡；主队同角色的另一张卡可以支援。支援贡献为 `floor(综合力/3000)` Pt。每队重算支援机会成本，不据此删除主队候选。

## 搜索与证明

单队搜索枚举道具配置和角色组，每个所选角色选一张卡，复用 Rust 参数／计分运算，不填入假歌曲调用三队搜索。

向上包围的综合力和技能区间上界放宽条件／位置约束。每个时间上界覆盖原触发到最晚排队开始加持续时间的并集，使用候选卡／条件／外部技能中的最长时间向上递推，故意高估可能覆盖；旧固定窗口上界在新规则下不安全。角色后缀 DP 对综合力 P、基础加权技能系数 K、加成与恰好一名合格队长给出上界；再为三个正数 t 求 `tP+K/t` 上界。P、K 非负，因此 `Pmax*Kmax` 与 `(max(tP+K/t))²/4` 都是上界，取较小者仍安全。共享数值包围覆盖重排、技能倍率和加权整数转换，协力房间估计以 256 次运算的舍入因子包围加权倍率的乘法与累加。协力系数分别最大化每名玩家的加权位置贡献，放宽位置互斥约束；原来的 1/5 系数在新规则下不安全。活动上界独立放宽自身与外部项，不用“房间分上界减自身分上界”构造不安全上界。

谱面系数、排队窗口包围、技能／加成后缀表和支援上限在每次请求中只准备一次。窗口求和以 binary64 的“持续时间、技能增分包围”原始位复用；每次查表前仍计算技能增分包围并检查失败。缓存至多包含每卡四个条件及四个外部技能，准备结束后释放。综合力与关联的 `tP+K/t` 表仍按配置计算。角色分组顺序固定，组内卡牌排序不改变后缀最大值。这项改动消除重复工作，保留上界运算和遍历优先级。

普通活动公式的 Pt 搜索增加按加成分档的后缀 DP，覆盖个人／协力及公式版本 0/1/2。每卡加成仅在此上界中向上归入 1/32 的精确二进制档位；对各角色后缀、剩余卡数及总档位，分别包围综合力和零名／恰好一名队长的技能系数。已选前缀与每个可达后缀档位给出独立的自身分及外部玩家分上界，送入原活动上界公式，再跨档位取最大值，覆盖所有可能完成。它保留分数与加成的关联，不假设实际协力 Pt 随综合力单调。实际加成、计分及合格卡库均不变；加成求和与舍入先包围，再执行单调的百分位四舍五入。已有当前最优解且原上界不能剪枝时，才尝试此检查；仍保留等分分支。零加成、总档位超过 128、不支持的活动规则或不安全运算均沿用原上界。分档表的有界内存在分配前计入预算估算。

只在上界严格低于当前最优目标时剪枝，保留等分分支处理平局。已证明无解的分支可在首解出现前关闭。未知、非有限或可能溢出的上界不能剪枝。轮询保留超时／取消语义，算术／补算失败不得成为 `exact`。

存储随卡牌、角色、音符和保留结果增长，不物化全部五卡组合。搜索前用保守工作区估计检查 Worker 预算，其中为有界的时间缓存和站位映射预留 1 MiB；每次完整队伍计分前也检查停止请求。`estimatedSearchStorageBytes` 是估计，不是浏览器 RSS、WASM 堆容量或进程硬上限，不含输入序列化及运行时开销；重计算仍在主线程之外。

## 单曲／组曲对齐审计

新增的两项**技能执行模型**是加权顺序／站位模型和技能结束后的排队。它们导致的覆盖区间、期望和最高分概率变化都属于这两项；这不意味着不同演出模式的计分和结算规则完全一样。

| 环节 | 共用契约或保留的模式差异 |
| --- | --- |
| 档案、区服主数据、技能 | 同一 `buildSearchRoster`、实体 ID、排除规则、CN null 回退与显式零值、技能等级／持续时间、完整队伍乐队／属性条件。只有外部玩家独立提供条件输入。 |
| 角色及队伍参数 | 同一 v4 分项取整、已拥有道具配置、适用条件、小数综合力和队长居中的累加顺序。活动类型决定加成作用于综合力还是 Pt；组曲始终使用自己的综合力加成规则。 |
| 谱面与技能边界 | 同一计分音符、六次触发、同拍稳定排序、BPM 锚定时间、触发音符排除、起止端点包含、不加 epsilon。只有单曲调度实际开始时间。 |
| 音符计分及技能化简 | 同一 binary64 系数、判定／技能倍率函数、覆盖音符计数和两次分阶段取整。两种模式均未增加生命、原生 f32 或采样判定模型。新窗口函数对照所有共享技能行为及 P=0／0.73／1。 |
| Combo 与 Fever | 固有模式规则：单曲重置 Combo，上限 1.11；组曲跨曲继承，上限 1.34。单曲协力／团队演出使用 Fever，组曲没有。 |
| 顺序与第六技能 | 单曲个人／协力均使用 1024 路径／96 顺序权重，分别优化卡牌／玩家站位；协力第六技能跟随所选玩家。组曲保留均匀 120 顺序及中央队长第六次发动。 |
| 期望与最高分 | 单曲保留小数期望并在合格站位中最大化，最高分概率对应最高分站位并汇总并列顺序。组曲先对每曲均匀期望取整再相加，最高分输出保持既有契约。不增加全卡库最高分目标。 |
| Pt、房间分及支援 | 固有活动契约：单曲把 E(score) 代入对应活动公式，保留房间估计／取整及任务支援；组曲把三曲总分代入自身公式。Live Boost、CP、名次和胜负选项仍属于展示。 |
| 展示与序列化 | 相同的综合力显示函数与整数分数格式化函数；组曲合计显示先逐队转 f32 再求和。单曲支援保留明确的 floor。两者使用同一 Rust JSON 解码器，不暗改数值解析。 |
| 搜索与交付 | 单队和三支互斥队伍的搜索、稳定平局规则有意不同。两者均保留不安全上界不剪枝、如实报告 incomplete、补算复核及真实 Worker／WASM 交付。 |

此次审计额外纠正了单曲的参数累加顺序。组曲 v4 的规范化、参数／计分实现、搜索和补算保持冻结。未来对齐组曲应明确移植两项技能执行能力，同时保留上表所列模式规则；直接套用单曲结果公式会改变组曲契约。

## 已确定的优化方向

按优化目标分阶段推进：先建立期望分数搜索基线，并在测量支持时改善性能，再优化 Pt 额外引入的取舍。分数和 Pt 保持同一搜索框架，按目标使用不同的上界与遍历优先级。目标定义、活动公式、取整、站位分析和暂缓实施的最高分选队搜索均维持上文约定。

加权顺序和完整 0.75 秒排队已完成正确性及交付基线检查。首项期望分数优化复用请求内不变的上界准备；普通活动公式的 Pt 搜索也已采用上述加成分档上界，计分与遍历保持不变。同 Pt 次级期望剪枝、按分支收紧支援、协力完成 DP 和个人位置匹配上界，仍作为由剩余实测瓶颈决定的独立后续选项。全卡库最高分搜索继续暂缓。精确性指上述连续时间、解析化简模型内的精确性。

最初优化以完成主线 #216／#218 对齐、技能排队和队长参数累加顺序修正的单曲 v3 为基线，协力加权站位使当前规则进一步升级为 v4。这些属于正确性更新，不是性能实验。单曲验证输入重新生成；组曲使用完全相同的输入字节，对照已验证并冻结的 v4 基线。组曲规则、计分、搜索、最优解的稳定平局裁决和证明语义必须保持不变。共享规范化、JSON 数值解析、参数运算、计分与组曲上界均不在后续优化范围内。Rust 改动仍需重建共享 WASM 包，因此隔离必须由回归证据确认，不能只依赖文件边界。

1. **期望分数阶段：**用个人演出和协力评估共用分数上界、分支开销，以及找到较好解的速度。复用已完成的分数及分数关联冒烟场景，并为留存 Pt 案例增加只将目标改为分数的对照，保留活动对综合力的影响和其他全部输入。只优化测量确认的共性瓶颈，每次实验一项改动，计分保持不变。本阶段完成正确性、覆盖与既有预算内的性能基线确认即可，不要求穷尽所有分数优化后才进入 Pt。
2. **Pt 阶段：**首项改动按加成档位约束综合力和技能系数，先处理留存的协力超时，再用同一套零名／一名队长 DP 覆盖个人演出，遍历顺序保持不变。Pt 相同时的次级期望上界、面向 Pt 的遍历顺序、按分支收紧任务支援，仍是独立后续实验，由剩余实测瓶颈决定是否实施。Pt 仍搜索完整合格卡库，不能先筛出分数最优队伍或分数前 N 名，再只在这个子集内最大化 Pt。

每项新剪枝规则都必须对照独立的小规模完整枚举，覆盖部分分支、取整边界和平局。保留向上数值包围与未知上界不剪枝，不截断候选卡池。各阶段先验证对应目标案例，再以相同的 30 秒搜索预算重跑完整 32 场单曲冒烟子集，并执行相关公开检查；共用搜索改动还需覆盖新增的分数对照案例。比较耗时、访问分支数、完整队伍评估数、找到当前最优解的时间、精确完成情况和内存；不能仅凭分支减少宣称提速。

仅涉及单曲私有实现的迭代，对重建的 WASM 执行公开绑定测试；只有具体的未解决风险才增加组曲代表案例。仅重建共享包或到达阶段节点，都不触发完整 80 场组曲对照。只有组曲或其依赖的共享逻辑／交付边界实际改变、出现组曲回退证据，或用户明确要求时，才执行完整对照。以相同输入和预算检查精确最优结果、稳定平局、证明行为及保留队伍补算。重建包时检查 WASM 体积和初始化；存在相关性能风险时再测组曲耗时。相关源码、产物和环境等价时复用已通过证据。记录代码及产物来源；历史归档本身不能证明变化后的行为通过验证。

正确性对照复用冻结的输入字节、已验证的基准输出、规则版本及源码／产物哈希。日常迭代只运行新实现，不为重新得到已有答案而重跑未变化的旧算法。只有缺少新输入的基准、需要核查具体基准异常，或确需重测少量代表案例的耗时，才运行旧实现。旧基准的 incomplete 仍是不完整证据。既有计时注明环境与日期后复用；不可比时只报告新耗时，不据此宣称精确提速倍数。正确性核对与性能重测分别决定。

## 交付与兼容

- [`single-source.ts`](../../src/lib/bandori/team-builder/single-source.ts) 将 UI 活动／设置策略接入共享组曲卡库／谱面规范化。
- [`single.rs`](../../crates/bandori-medley-search/src/single.rs)、`single_score.rs`、`single_upper.rs`、`single_event.rs` 负责单队搜索，共同计分仍在 `exact_score.rs`。
- 规范化版本为 `hhwx-single-search-input-v1`、`hhwx-single-medley-foundation-v4`，旧版本及未知版本校验失败。
- `runSingleSearchJson` 通过现有 `medley-wasm/pkg/` 交付。生产 Rust 改动后须重建，Worker 导入图与 WASM 资源共同更新。
- 公开档案／主数据／谱面 API 及持久化卡牌 ID 不变。页面默认开启外部技能条件，旧演出偏好缺少 `conditionSatisfied` 时也按开启迁移；已明确保存的 false 仍为 false。页面始终发送布尔值；底层适配器调用方若省略该字段，仍按基础技能效果处理。旧 TypeScript 可调用搜索导出删除，`bandori-team-search.ts` 只保留展示／设置类型。历史比较必须显式指定干净的退役前检出。
- 组曲使用 `hhwx-medley-bestdori-v4`；输入 schema、均匀顺序计分、三曲搜索和输出语义保持不变。

`npm run test:team-builder` 使用实际生成绑定，对照独立逐音符／站位／顺序枚举，覆盖区服回退与零值、端点、Fever、Combo 上限、Pt、支援、协力输入和中止／错误。Rust 测试对照完整枚举验证搜索及每个部分分支上界。共享来源和组曲绑定受影响时继续回归，见[组曲测试](medley-testing.zh-CN.md)。浏览器必须实际运行 Worker 和重建后的 WASM，检查进度、最终状态、取消与展示；仅构建不能证明这些路径。

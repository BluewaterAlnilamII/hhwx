### Design and experience requirements

| ID | Required behavior | Boundary |
| --- | --- | --- |
| R1 | Empty @ recommends distinct recent speakers, up to eight; fewer candidates remain fewer. | Preserve room/retention scope. Presence does not filter/rank recommendations or fill spare rows. |
| R2 | A name/UID query searches all eligible accounts. | Exact name/UID, prefix, then substring; stable UID tie-break. Neither recency nor presence affects ranking. Eight limits display only. Self, offline and invisible accounts retain eligibility. |
| R3 | Completed results keep their candidate accounts, order and selection stable. | Changed input or reopening computes the next result, preferably from cache; the first pending request may finish once. ### Implementation checklist

1. **Restore candidate sources and ranking (R1, R2).** Update `chat-mentions.ts` and callers to remove online keyword weighting and online fill for empty suggestions. Keep distinct recent speakers for empty queries; keyword queries use profiles without message-history work. Verify presence changes do not alter ranking for the same input, fewer than eight recent speakers stay fewer, and a complete UID finds accounts outside the first eight.
2. **Stabilize each completed displayed query (R3, R4).** Update `ChatComposer` to obtain candidates for an opening/input change and preserve that result and selection once complete. Underlying recent-user/profile changes feed the next query rather than driving current rendering. Remove reinserting a displaced selected account into row eight. Changed input still cancels/ignores stale results; preserve IME, Esc, Enter/Tab, pointer and keyboard behavior. Verify User1 going offline cannot change the default to User2, selected User2 cannot move from row two to eight, and a new User12 message cannot replace the first entry of an already-open empty @. Selection must act on the account currently shown.
3. **Decouple message deletion from default recommendations (R1, R3, R7).** Remove deletion-driven request cancellation, cache invalidation, candidate filtering, previous-message lookup and refill. Remove recommendation-only `lastMessageId` and its comparisons; retain timestamps for ranking. Remove SQL's lateral lookup of the latest message ID for each of the eight candidates. Preserve deletion records needed by messages, replies and unread handling. Adjust the RPC through a new migration and check actual deployed consumers: released `fbda0c06` needs no intermediate rollout, while field-dependent development consumers must migrate before removal, as detailed in the integration guide. Do not rewrite applied migrations or silently break response dependencies. Verify deletions during or after loading add no recommendation reads or candidate removals; the initial read still runs once. An independently required later load may naturally use current data.
4. **Prevent reaction updates from resetting reading (R6, R7).** Update `ChatSession` merging/buffering: loaded messages retain versioned reaction state; temporary updates serve messages not yet loaded and in-flight reads, with merge/deletion/session cleanup. Remove the reset after 1,000 entries instead of raising the threshold. Preserve early reactions, stale history/context responses, and independent ordering of totals and the viewer's own selection. Verify 1,001+ messages and reaction events cause no truncation/jump/history read and retain the existing race guarantees.
5. **Share a reaction preview and full dialog's first page (R5, R7).** Share current preview results with the full list, reusing completed/in-flight first pages by message, emoji and reaction version, including the pagination cursor. Closing a preview must not cancel a request still used by the dialog; retain retry and lifecycle cleanup. Preserve open-dialog browsing state; version changes affect subsequent openings/reads without adding live refresh. Check shared comment consumers. Both hover-then-open and open-during-hover-request must read the first page once; pagination still works.
6. **Remove no-op mention writes and repeated readbacks (R6, R7).** With a successfully loaded, valid complete inbox, acknowledge only known unread IDs; an incomplete inbox still permits visible off-page acknowledgement. Successful acknowledgement removes IDs locally; the account-scoped notification carries room/acknowledged IDs for idempotent handling in same-account views. Own echoes do not reload the whole inbox. Coalesce a read only for required refill, incomplete data or concurrent new/invalidation events. Prevent stale GET responses from restoring confirmed notices and keep failures from consuming reminders. Preserve new-mention and initial/recovery reads. Added notification fields let old clients retain their readback behavior. The reproduced complete-inbox PUT + GET + GET becomes one PUT and zero GET; already-read history causes zero PUT. Test more than 50 entries, two tabs, duplicate events and request interleaving. Moving the same full SELECT into PUT is not a database optimization.

### Known limit and explicit exclusions

- **User-list freshness is unresolved.** The cache can omit later registrations or retain an old name; existing local matches suppress fallback search. Preserve the current on-demand load/fallback in this batch and do not claim instant freshness. Decide separately whether registration/renaming must immediately enter other users' searches before choosing a mechanism. Registration/profile broadcasts and presence-profile merging are not required fixes in this batch and cannot modify an active result.
- **Withdrawn behavior is not backlog.** Do not add live participant-dialog refresh, deletion-driven recommendation repair, online ranking/fill, modal-wide read suspension, a frontend invisibility switch, refresh prompts or additional search controls.
- **Necessary reads remain.** Do not remove authorization, initial snapshots, actual recovery, pagination/context or inbox refill just to lower request counts. Committed changes whose publication fails still rely on a later on-demand snapshot; no outbox, extra channel, activity-summary table, version infrastructure or dependency is added here.

## Activity, unread state and native recovery

A signed-in tab owns one chat connection. `chat_activity:main` stays subscribed while the dialog is closed; `chat:main` is a token-authorized client subscription enabled only while the dialog is open. Personal account notifications retain their existing implementation. Guests create neither subscription.

- Login subscribes to activity before reading `GET /api/chat/activity`. It returns only `{latest,latestOther}` cursors, without bodies, author profiles or unread counts. Creates publish a cursor and author ID; deletes publish an ID. Text and image messages from other accounts can light the launcher's red dot; own messages and stamps cannot.
- The durable `(createdAt,id)` read cursor lives in `localStorage`, scoped to account and room. First use initializes at the current latest position without flagging old history. Other tabs in the same browser accept monotonic storage updates; cross-device read synchronization is outside scope. A read advances only after the visible, focused dialog renders the latest bottom. Opening an older reading position does not mark it read. Broker offsets are never used as read cursors.
- First opening subscribes to full messages before requesting `GET /api/chat/messages?activity=1`. One service-only `read_chat_snapshot` RPC returns the latest 50 messages plus the activity summary from one database snapshot; incoming publications are buffered during that read.
- A valid cached baseline plus `recovered:true` uses SDK replay directly, with **zero history requests**. The retained subscription object carries its recovery position across close/reopen. Create/delete application is idempotent; ephemeral stamps use `skip_history:true` and never replay.
- If recovery fails or no valid baseline exists, fetch one fresh latest page, replace the old loaded history and return to latest. Preserve drafts, pending uploads, failures and the local read cursor. Do not validate retained IDs, stitch disconnected history or page forward to close a gap. A closed dialog refreshes only its summary; message history waits until opening.
- Closing preserves loaded message records, pagination and the scroll anchor, releases confirmed media previews and unsubscribes full messages. Pending attachments/uploads remain owned by the account. Hiding or blurring pauses read acknowledgements without disconnecting. Stamp playback requires only an open dialog, regardless of page focus or visibility. Hiding the page neither drops new effects nor clears current effects/audio; their existing lifetime continues without queuing for the foreground. Closing still cancels playback. Browser background scheduling and audio policies still apply. Logout/account change disposes the account's memory and transport.
- Cached reading, navigation and HTTP send confirmations remain usable during reconnect. A history failure retries that read without tearing down a healthy socket. Message, activity and presence state do not poll. A deletion of a current summary marker triggers one coalesced summary refresh; ordinary arrivals do not query.

Both namespaces retain at most **256 events for 300 seconds** in Centrifugo's memory engine, with forced recovery. Either count or age can exhaust the window; restart loses it. These are short-disconnection bounds, not durable delivery. A database commit whose publication fails is outside this guarantee and becomes visible at a later fresh snapshot. An outbox remains deferred.

Apply `20261026072628_chat_activity_and_snapshot.sql`, then the new broker configuration, then the app. The migration only adds two service-role invoker RPCs with a fixed empty search path; it adds no table or read-state writes. New tabs opt into the activity connection with `POST /api/chat/connection?activity=1`; legacy requests retain their old full server subscription. Existing before/after history APIs remain compatible, although the new client no longer uses forward recovery. Rollback can keep the additive RPCs/history configuration and restore the old app. No production operation is part of this local change.

The reference is Discord's separation of passive activity and active message delivery, and its resume-or-initialize lifecycle, not a copy of its private web-client protocol: [passive sessions](https://discord.com/blog/how-discord-reduced-websocket-traffic-by-40-percent), [Gateway resuming](https://docs.discord.com/developers/events/gateway#resuming), [Centrifugo recovery](https://centrifugal.dev/docs/server/history_and_recovery). The actual implementation uses the installed Centrifuge SDK.

## Input and sending

1. Count raw Unicode code points including whitespace, capped at 1,000. Trim on submission; ignore whitespace-only input. IME selection must not send; Enter sends, Shift+Enter inserts a line.
2. Each submission immediately clears the composer and appends a pending message with its own request UUID. Further typing/submission remains available.
3. HTTP sends run sequentially. WebSocket readiness, reconnection, history synchronization and another outstanding send do not lock the composer.
4. Each message displays queued/sending/failed state. API fetches time out after 30 seconds and image PUTs after five minutes, releasing the queue into existing manual-retry behavior. Retry keeps its request ID and never replaces a newer draft. A new message with identical text gets a new ID.
5. Merge HTTP acknowledgements and publications by UUID. HTTP success remains visible without the socket, and an older history response cannot erase a newly confirmed message.
6. Known quota, mute, authentication/network failures stop further ineffective queued requests and retain them for manual retry. No durable offline outbox or unlimited automatic retries.

## Quota and database

- Each account has 20 successful new sends per 60-second window beginning with its first save. Devices/tabs share quota; bursts are allowed, including at fixed-window boundaries.
- Retries spend no additional quota; failed saves spend nothing; deletion does not refund; a saved message counts even if publication fails. Display the returned retry time locally without polling.
- CLI-created forward migration `20261023205032_chat_sending_and_query_cleanup.sql` replaces `user_state.next_send_at` with a window start/counter, preserving messages and mutes. The existing `nextSendAt` response becomes the exhausted window's deadline, otherwise null.
- One Auth `getUser` call followed by one save RPC. Lock only the actor's state, check idempotency/mute/quota, insert and update quota in the same transaction. Existing state rows are not repeatedly inserted.
- No `account_status` reads, history counting for quota, scheduled reset or separate quota request. Read author existence/display fields together, read viewer state once, and join authors after limiting the history page.
- Keep two private tables, service-only invoker RPCs, RLS/grants, request UUID uniqueness and cursor/retention indexes. Browser roles cannot access tables/RPCs directly.
- Deletion/moderation still check ownership/roles in SQL; removing email queries does not remove these business permissions.

# OurNotes card pages

[简体中文](ournotes-cards.zh-CN.md)

The catalog follows the existing Bandori card list and event tab layout. Both catalogs use the same page shell, card-row markup, detail header, server controls, information rows, stats footer, filter primitives, count badge, help popover, loading states and full-image viewer. OurNotes keeps its own card semantics and five-slot regions; the existing Bandori entry points forward to the extracted shared implementations.

## Routes and state

- `/ournotes/cards` opens Member; `?kind=support` opens Snapshot (留影 in Chinese). The two equal-width tabs share one list implementation. Character filter buttons are ordered by numeric character ID ascending.
- `/ournotes/cards/{member|support}/{cardId}` opens a detail. Invalid kinds, IDs and missing cards return not-found; reader failures use the route error/retry surface.
- Filters use `q`, `available` (slot codes), `bands`, `attributes`, `rarities`, `characters`, and `direction`. Missing selection keys mean all; explicitly empty values mean none. Selections are OR within a group and AND between groups. A Snapshot can match any of its characters or bands.
- Tab changes retain common filters and reset rarity selection. Clearing retains the current tab. The initial batch is 40, with 40 more per action; query changes reset that batch. Sorting is limited to card ID, descending by default. Rarity, attribute and power sorting are not supported; old unsupported `sort` values resolve to ID and are removed when filters, tabs or return links are rebuilt. Source `startAt` is not treated as a verified release date.
- The toolbar exposes separate Bandori and OurNotes preferred servers, both presented as CN by default, independent of UI language. OurNotes CN is the existing CN_INTL slot. Explicit choices persist separately in browser storage (`hhwx:bandori:preferred-server:v1`, unchanged, and `hhwx:ournotes:preferred-server:v1`); reading defaults does not write them. Both use the same persistence implementation. Blocked or invalid storage keeps the default, and in-memory selection still works when writes fail.
- Each catalog card uses the OurNotes preference when available, otherwise the first available slot in JP, EN, TW, CN_INTL, KR order. Its title, name, skill summaries and detail link use that resolved slot. Individual missing card/skill texts remain missing; generic character/band filter labels may fall back. Availability filters only filter membership and never change the display preference. Legacy list `server` parameters are removed while retaining other query parameters and the hash.
- Details use `server=jp|en|tw|cn_intl|kr` and also accept `server=cn` for the same slot. A valid available URL server wins over the preference. Missing, invalid or unavailable servers resolve after preference hydration and replace the URL with the available result, retaining the list query and hash. Detail server switches affect that URL only, not the saved preference. The wire identifier remains `cn_intl`; UI labels, icon titles and search present it as CN. Metadata without a valid available explicit server uses the generic localized catalog title until resolution. UI language controls labels and formatting, never regional data selection.
- A detail's `list` parameter holds the previous list query. The back link accepts only known filter keys and reconstructs a local catalog URL. Filters stay in the URL; only the two explicit server preferences are persisted.

## Data and display

The shared stats footer shows Member's three integer parameters and total power. Snapshot shows only its three independent percentage bonuses, each with two decimal places, in three equal columns; they are not added into a total. API `powerMax` stays raw: `3500 / 10000` formats as `35.00%`. This matches the JP native `UISupportCardDetailView.UpdateView` (RVA `0x5cd5288`), whose three formatters at `0x53c7068`, `0x53c7100` and `0x53c7198` divide the raw parameter by 100 before displaying the percentage number. These remain the card definition's maximum parameters, without player growth controls or team bonuses.

Thumbnails preserve their native aspect ratios: Member widths are 64px below 640px and 88px at or above 640px; Snapshot widths are 128px and 160px respectively. OurNotes enables the shared `CardCatalogRow` mobile layout, with artwork and basic information above full-width skill rows. Desktop keeps artwork beside all text. Typography, panel styling, padding and arrows remain shared; Bandori retains the default layout.

Catalog rows show each existing skill's level-5 effect text on its own row, without category prefixes. Member order is Leader Skill, LIVE Skill, GEKISO Skill; Snapshot shows LIVE Support followed by GEKISO Support, preserving the source slot order within each category. Zero-ID slots are omitted. Two support skills occupy two separate rows even when both belong to the same category; missing categories do not add placeholder rows. A referenced skill with no regional description still shows the unavailable-text message. Each summary uses the shared row typography and its own text clamp so a long summary cannot hide the following rows.

The browser loads only the active card kind, plus characters, bands and skills, from the existing [master API](ournotes-master-api.md). These independent requests run together through `useCachedFetch`. The public image index uses the existing URL-keyed index cache. Initial dependency loading has one page-level state; failed dependencies can be retried without reloading successful ones. Last-good data remains visible after refresh failure. Server-rendered card details and metadata use the existing private reader, never public CDN metadata or self-HTTP calls.

Search shares Bandori's toolbar, example rendering, tokenizer, comparison boundaries and server aliases. NFKC/case normalization, token intersections, immediate input clearing and IME protection follow the Bandori contract. Official band names and full/short character names match identity; no abbreviations or nicknames are inferred. Multilingual card titles are searched by `/name` or straight/Chinese quotes, excluding character names and skill text. Unknown text searches card titles, displayed names, character names and band names. Bare positive safe integers and `#ID` match only card IDs; malformed explicit conditions never fall back to text. Rarities use the explicit order **R < SR < EX < BD < SSR**, not their numeric IDs. Both filter buttons and comparisons use that order; Member omits EX and Snapshot offers all five, including rarities with no current cards. `SR+` / `>=SR`, `EX-` / `<=EX`, `>BD` and `<SSR` compare rarity only. Server searches accept Bandori's JP/EN/TW/CN aliases, `cn_intl` as a compatible CN alias, and KR/Korea/韩服 aliases. Both `available=cn` and `available=cn_intl` select the existing slot; generated URLs retain the wire code.

Reviewed band aliases match identity: MyGO reuses Bandori's `mygo!!!!! / mygo / mg / go`; Ave Mujica adds `avemujica / mujica / ave`; Mugendai MewType adds `mewtype / 梦限大 / 夢限大 / ゆめみた / yumemita`; Ikka Dumb Rock! adds `一家 / ikka / dumb rock / dumbrock`. millsage uses its official name. No `am / ms / idr` or new single-letter band aliases are registered. Recognized aliases never fall back to card text when their identity has no matches.

Character search also derives surnames by removing the same-language short name from the end of the full name, or from its start when followed by a space (English given-name-first order). Slash-separated stage and personal names are registered separately: `Doloris` and `三角初华` are full-name keywords, while `三角` is a surname and `初华` is a short name. Each matches the same character ID, including that character's Snapshots, without matching unrelated card titles. Known personal names additionally accept joined/spaced surname-given-name and given-name-surname forms, such as `千石ユノ` and `minetsukiritsu`; this does not remove punctuation from general search text. Combined source names remain accepted; slash-prefixed or quoted queries still search only card titles.

MyGO characters reuse the reviewed Bandori aliases through the explicit ID mapping `36→1, 37→2, 38→3, 39→4, 40→5`, including `tmr`, `rana / raana`, `素世`, `shina` and the already-reviewed nicknames. Nyamu additionally accepts `yutenji / yuutenji` and their joined/spaced full-name forms in either order. Original macron spellings remain valid; no general accent folding, inferred nicknames or new initialisms are introduced.

Acquisition types, skill types and skill effects are outside the current search scope. No skill names/descriptions, effect categories, score percentages or duration values are indexed for search. Existing skill displays remain: descriptions replace `{n}` with `descriptionParameters[n][level - 1]` as plain text. Zero skill IDs are absent; source slots retain their internal identity, but displayed category labels have no 1/2 suffix. Two skills of the same category remain separate entries with the same category label. Member names fall back to character names only when the card's `name` field is absent, not when a localized string is empty.

One outer detail panel contains the shared header, artwork, card information with the maximum-stats footer, and a separate Skills section. The explicitly approved Skills section offers levels 1–5 and defaults to level 5; skill names and effects use the same detail rows and typography as Bandori. Skill names show only the selected region's text, without a secondary Japanese name. Below the shared detail columns' 54rem container breakpoint, each skill groups its left-hand category and right-aligned name above a full-width, right-aligned effect. Only skill groups are separated by lines; the repeated effect label is visually hidden but remains accessible. Wide layouts retain two columns. Descriptions use normal whitespace and natural wrapping in both catalog and detail, without altering source text or parameter substitution. No growth tables, upgrade expenses or resource lists are displayed. Their API fields remain unchanged. No acquisition filter, release-time conversion, player level/Rank, team calculator, costume/voice links or comments are inferred from unsupported data.

Skill category labels follow the international client MasterText entries `leader_skill`, `live_skill`, `gekisou_skill`, `live_support` and `gekisou_support`: Leader Skill / 队长技能, LIVE Skill / 演出技能, GEKISO Skill / 激奏技能, LIVE Support / 演出支援 and GEKISO Support / 激奏支援. Snapshot / 留影 is also confirmed by `ui_bili_formation_power_snap`. These labels were checked against the retained 2026-10-01 EN raw MasterText (SHA-256 `7f8a55dc415d0cb4b5f8eb79c1a024090511a4b3685e9ccf035bf9149f14a751`). API identifiers such as `gekisou`, `supportSkillId01` and `supportSkillId02` are unchanged.

## Artwork provenance

Detail pages show the full artwork without the thumbnail frame, shadow or attribute overlay, preserving the image aspect ratio. Catalog thumbnails retain those decorations. Both modes share the image loading/error handling and the existing full-image viewer.

Card images resolve by **assetId**, kind and variant through `https://cdn.hhwx.org/ournotes/cards/index.json`; missing variants stay unavailable. Index descriptors must use the expected SHA-256-addressed path. Failed image state follows the source URL, so switching cards does not inherit a previous image failure.

Fixed UI uses the assets-builder's reviewed JP sprites and prefab measurements, recorded in `hhwx-assets-builder/docs/research/ournotes-card-ui-2026-09-28.md` and its adjacent JSON. The frame reference sizes are Member 224×294 and Snapshot 326×184, with six-unit artwork insets and an unclipped 50×50 attribute overlay centered at (16,18). Nine-slice borders are preserved for `FrameSquare_6px`, `FormationSupportCardOutline` and `FrameMemberThumShadow_9slice`. Rarity palettes remain separate, with angles 90°/128°. Fixed sprites are not added to the card index or another configuration API. Rarity and player Rank are distinct; directory cards show no player level or Rank.

Frame colors follow the native `UIGradientImage` mesh behavior, not hard SVG color bands. The JP ARM64 implementation (`ModifyMesh` RVA `0x6314cf8`, `CreateGradientMesh` `0x6314d98`, `SetVertexColor` `0x6314f58`) splits axis-aligned geometry at gradient keys, evaluates the gradient at vertices, then lets the rasterizer interpolate vertex colors. SSR's [Fixed mode](https://docs.unity3d.com/ScriptReference/GradientMode.Fixed.html) controls vertex sampling, not a stepped final image. Member therefore uses smooth stops at key/slice vertices; the 128° Snapshot keeps its nine-slice triangles and projects coordinates across the actual 326×184 bounds. SVG gradients reproduce each triangle's vertex colors; triangles with three different colors combine isolated RGB planes. Native Member Replace and Snapshot Multiply modes are equivalent for these prefabs' white vertex color. Geometry is shared across rows; sprites, masks and artwork remain unchanged. No pixel-for-pixel equivalence is claimed for Unity color quantization, color-space configuration or browser edge rasterization.

Server controls reuse the existing local JP/EN/TW/CN icons (`CN_INTL` uses the CN icon). The KR icon was copied from [Bestdori’s server icon](https://bestdori.com/res/icon/kr.svg) on 2026-10-02 to `public/res/server-icons/kr.svg`; SHA-256 `b5defb8a0aed8a9ca429e6cdcb1ecb9590ede92bcdf2edf5d6ee6eda4cf6df37`. Existing immutable icons are unchanged.
